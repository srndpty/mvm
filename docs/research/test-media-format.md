# 検証素材の形式仕様 (S2)

生成: `scripts/make-testmedia.ps1`
読み取り: `mvm_bench decode --expect-marker` ([tests/harness/mvm_bench.cpp](../../tests/harness/mvm_bench.cpp) の `readMarker`)

---

## 目的

Phase 0 の判定には「要求したフレームが本当に取り出せたか」を**機械的に**確かめる手段が要る。
これが無いと以下が判定できない。

- V2: 素材を正しく decode できているか
- V4: seek が要求フレームに正確に着地するか (M4 は 100% 一致を要求する)
- V6: proxy と original でフレーム番号がずれないか
- V12: preview と final render が同じフレームを指しているか

目視やタイムコードの OCR には依存しない。**OCR は前提にしない。**
理由は 3 つある。

1. 圧縮で文字が滲むと誤読する。誤読は「seek がずれた」と区別できない
2. フォント・レンダラに依存すると、環境が変わるだけで検証が壊れる
3. 遅い。数百フレームを毎回検査したい

代わりに、フレーム番号を**大きな高コントラストの矩形の並び**として焼き込む。
読み取りはセル中心の輝度を閾値判定するだけで済む。

---

## マーカーの配置

映像の左上、原点 `(0, 0)` に帯を置く。

| | 値 |
| --- | --- |
| セル幅 | 64 px |
| 帯の高さ | 64 px |
| セル数 | 19 |
| 帯の幅 | 19 × 64 = **1216 px** |
| 白レベル (bit=1) | 輝度 235 |
| 黒レベル (bit=0) | 輝度 16 |

```
 x=0    64   128  192            1088 1152 1216
  +-----+-----+-----+-- ... --+-----+-----+
  |sync |sync | b0  | b1      | b15 |sync |   y=0..64
  |white|black|     |         |     |white|
  +-----+-----+-----+-- ... --+-----+-----+
  cell:   0     1     2    3        17    18
```

| セル | 内容 |
| --- | --- |
| 0 | 常に白。同期 |
| 1 | 常に黒。同期 |
| 2..17 | フレーム番号の 16 bit。**LSB first** (cell 2 = bit 0) |
| 18 | 常に白。終端同期 |

16 bit なので 0..65535 フレームを表せる。60fps で約 18 分。
Phase 0 の素材 (最長 60 秒 = 3600 フレーム) には十分。

帯は 1216 px 幅なので 1920 と 3840 のいずれにも収まる。
1216 px 未満の映像には焼き込めない (Phase 0 の素材には該当しない)。

## 読み取り手順

1. フレームを RGBA で取り出す
2. 各セル `i` の中心 `(i*64 + 32, 32)` を中心とする **8x8 画素**を平均する
   - 1 画素だけ見ると圧縮ノイズで誤読する
   - 8x8 なら H.264 / HEVC の変換ブロック境界の影響も平均化される
3. BT.601 で輝度へ変換: `Y = 0.299R + 0.587G + 0.114B`
4. 閾値 **128** で 0/1 判定
5. **同期セルを先に検査する**: cell0 > 128 かつ cell1 < 128 かつ cell18 > 128
   - ここが崩れていれば、読み取り位置がずれているか素材が別物である
   - 同期が取れないまま数値を読むと、誤った値を「正しい」と誤認する
6. cell 2..17 を LSB first で組み立てる

```
value = Σ (luma[2+b] > 128) << b     (b = 0..15)
```

同期セルは白・黒・白の 3 点で帯を挟む。これにより
「帯が無い映像を読んだ」「位置がずれた」「上下反転した」のいずれも検出できる。
パリティは持たない。同期 3 点と、後述の値域検査で十分と判断した。

### 呼び出し側が追加で行うべき検査

- 読み取った値が `0 <= value < frame_count` の範囲にあること
- 要求フレームと一致すること (`mvm_bench decode --expect-marker` が行う)

## 音声信号

既知の周期を持つ正弦波を焼き込む。A/V 同期の測定と、
音声が正しく読めているかの確認に使う。

| チャンネル | 周波数 | 48000 Hz における周期 |
| --- | --- | --- |
| L | 1000 Hz | 48 サンプル (整数) |
| R | 500 Hz | 96 サンプル (整数) |

いずれもサンプルレートの整数分周なので、位相は完全に決定論的
(`t=0` で振幅 0、上昇方向)。振幅は 0.5。

左右で周波数を変えているのは、チャンネルの取り違えを検出するため。

```
aevalsrc=exprs=0.5*sin(2*PI*1000*t)|0.5*sin(2*PI*500*t):s=48000:d=<秒>:c=stereo
```

### 日本語パスへの複製 (V10)

以下へ複製する。ディレクトリ名・ファイル名の両方に、
日本語・半角空白・**全角空白**・全角記号を含める。

```
素材\日本語 テスト\第1回　微分積分＆演習\

```

### アルファの検証方法

`png_alpha` のアルファは `(X+Y)*255/(W+H)` のグラデーションなので、
0 から 253 までの値を含む。

`mvm_bench probe` は pix_fmt 文字列を見るだけでなく、
**実際に取り出したフレームのアルファ値の最小・最大**を報告する
(`alpha_min` / `alpha_max`)。これにより
「MLT のパイプラインを通った後もアルファが生きているか」を判定できる。
pix_fmt が `rgba` でも中身が全て 255 なら、それはアルファが落ちている。

## 決定論性について

**ファイル hash の完全一致は要求しない。**

`libx264` / `libx265` はスレッド分割やレート制御に非決定要素を含むため、
同じ引数でも出力バイト列が一致するとは限らない。
hash 一致を合格条件にすると、本質的でない理由でテストが落ちる。

代わりに、再生成時は以下の一致を要求する
(`make-testmedia.ps1 -VerifyRegeneration`)。

- container / video_codec / audio_codec
- width / height / pix_fmt
- fps_num / fps_den (有理数のまま)
- frame_count
- sample_rate / channels

hash の差は情報として報告するが、失敗にはしない。

PNG と WAV は非圧縮または可逆なので、実際には hash も安定する。

## manifest

`<出力先>/manifest.json` に以下を記録する。

- 相対パス / SHA-256 / サイズ
- container / video_codec / audio_codec / pix_fmt
- width / height / sample_aspect_ratio
- fps_num / fps_den (有理数)
- frame_count / duration_sec
- sample_rate / channels / has_alpha
- **生成に使用した完全な FFmpeg 引数** (`ffmpeg_args`)
- ffprobe の生 JSON へのパス (`_ffprobe/<id>.ffprobe.json`)
- マーカー仕様 (セルサイズ・レイアウト・輝度レベル)
- 音声仕様 (周波数・サンプルレート)

`mvm_bench verify-media <manifest>` がこれを期待値として検証する。

### `expected` の必須フィールド

kind ごとに必須フィールドが決まっている。欠けていれば**失敗**とする
（黙って検証を飛ばすと「検証したつもり」になる）。

| kind | 必須フィールド |
| --- | --- |
| `video` | `width` `height` `video_codec` `pix_fmt` `fps_num` `fps_den` `frames` `sar_num` `sar_den` `duration_sec` |
| `image` | `width` `height` `video_codec` `pix_fmt` `sar_num` `sar_den` |
| `audio` | `audio_codec` `sample_rate` `channels` `duration_sec` |

`has_alpha` が真の場合は `alpha_min_le` / `alpha_max_ge` で値域も検証できる。

manifest 自体についても以下を検証する。いずれも失敗にする。

- `schema_version` が存在し、対応する値であること
- `assets` が存在し、空でないこと
- 各 asset に `id` / `relative_path` / `kind` / `expected` があること
- `kind` が `video` / `image` / `audio` のいずれかであること
- `id` が重複していないこと

### 破損・退化素材（`_corrupt/`）

`verify-media` の対象ではない。`probe` / `decode` が
これらを成功扱いしないことを CTest で確認するために置く。

| ファイル | 内容 |
| --- | --- |
| `zero.mp4` | 0 バイト |
| `random.mp4` | ランダムなバイト列 64KB（固定 seed で決定論的） |
| `truncated.mp4` | `v1080p60_h264.mp4` の先頭 20% |
| `text.mp4` | 拡張子だけ mp4 のテキスト |
| `subtitle_only.mp4` | コンテナは正当だが映像も音声も無い（字幕トラックのみ） |

`subtitle_only.mp4` は破損していない。「読めるが使えない」入力であり、
壊れたバイト列とは別の失敗経路を通る。ユーザーが実際に投入しうる形でもある。

## FFmpeg の固定

素材生成には **必ず** 以下を使う。

```
C:\msys64\ucrt64\bin\ffmpeg.exe
C:\msys64\ucrt64\bin\ffprobe.exe
```

ホストには `C:\tools` 版と winget 版の FFmpeg も存在するが、使わない。
PATH 上の別 FFmpeg へフォールバックもしない (見つからなければ失敗させる)。

mvm がリンクする libav* と同じビルドで素材を作らないと、
「MLT で読めない」のが素材側の問題なのか MLT 側の問題なのか切り分けられなくなる。

## 合成後のマーカー読み取り (S7 の所見)

**[事実] 合成後のフレームでは、マーカーのセル幅は 64px とは限らない。**

マーカーは素材の解像度に関係なく **64px セルの固定ピクセル**で焼かれている。
したがって素材の解像度と profile の解像度が違うと、
合成の過程でマーカーも一緒に拡縮される。

| 素材 | 素材上のセル幅 | 1920x1080 profile へ合成した後 |
| --- | --- | --- |
| 1920x1080 | 64px | 64px (等倍) |
| 3840x2160 | 64px | **32px** (0.5 倍) |
| 960x540 proxy (4K から生成) | 16px | **32px** (2 倍) |

**帯が占める幅の割合は拡縮しても保たれる。**
4K の帯は 1216/3840 = 31.7%、その proxy も 304/960 = 31.7% である。
だから 4K でも proxy でも、1080p へ合成すれば同じ 32px になる。

### 64px 決め打ちで読むと何が起きたか

**[事実]** 4K scenario の seek 計測で **314/314 が不一致**になった。
「seek 精度が壊れた」ように見えたが、原因は計測側だった。

セル幅の自動判定を入れたが、それでも 34 件中 16 件が不一致だった。
**64px で読むと偽の同期が成立していた**ためである。
実マーカーは 1920px 幅のうち左 608px しか占めていないので、
64px 換算のセル 10〜18 は映像本体を読んでいた。
たまたま同期 3 セルの明暗が合致し、frame 0 を 64512 と読んだ。

### 対処

同期の条件を「3 つの同期セルが正しい」だけでなく
**「19 セルすべてが白 (>200) か黒 (<55) に振り切れている」**に強めた。

マーカーは純白と純黒で焼かれているので、
正しいセル幅なら全セルが振り切れる。
映像本体は中間調が混ざるので落ちる。

これで 1080p native / 4K / proxy のすべてで代表フレームが一致した。

**[方針] 「読めなかった」を「一致した」にしない。**
セル幅が分からないときは `readMarkerAuto` が
どの候補でも同期しなければ `syncOk=false` を返す。
