# 数式 layer の書き出し高速化 P1: 字形の範囲だけを合成できるか

2026-10-12。[書き出しが進まなかった原因の調査](math-semantic-layout.md#書き出しが進まなかった原因の調査2026-10-11)
の続き。keyframe の間引きで尺に比例する劣化は消えたが、数式 1 層ごとに全画面を合成するコストが残り、
解の公式の Project（v4、6840 frame）は製品の条件では書き出せない。全画面の透過 PNG の代わりに字形の
ある範囲だけを MLT へ渡せるかを、試作と全画素比較で調べた。

**これは調査と最小試作の記録である。製品の合成経路は切り替えていない**（`TimelineExportRequest::
mathLayerStaging` の既定は `FullFrame`。それ以外は検証 harness だけが指定する）。`timeout_ms` の契約、
keyframe の間引き、過去の診断結果と FAIL の記録は変えていない。

証拠は `build/math-sparse-p1-20261012/`（run ごとの `identity.json` に source と runtime の SHA-256）。

## 結論

- [事実] 字形の範囲は全画面の中央値 0.125%（平均 0.38%、最大 4.9%）。合成対象の画素は減らせる。
- [事実] MLT の既存 API だけで、pre-YUV が**全画素・完全一致**する渡し方がある（左上の原点を保ち、
  字形の右端・下端より先だけを落とす `AnchoredBox`）。ただし合成対象は 29% までしか減らず、
  render は 1.9〜2.7 倍。
- [事実] 字形の範囲そのもの（`BoundingBox`）は render が 2.8〜5.5 倍になるが、端数位置では
  **完全一致しない**（差は全画素 1 階調以内）。整数位置だけ完全一致する。
- [事実] どちらの渡し方でも、v4 全体は製品の条件で完了しなかった。区間の fixture で見えた改善は、
  Project 全体では出ない。全体では、残っている keyframe の文字列化など、graph の大きさに比例する
  直列の処理が支配的である。
- 製品の 10 分 timeout は、この試作だけでは達成できない。

## 1. 現在の成果の保全と observer の確認

既存の診断結果・SHA-256・FAIL の記録、`timeout_ms` の契約、keyframe の間引きは変更していない。
observer（`MvmExportObserver`）のスレッド安全性を読み直し、2 点を直した。

| 項目 | 確認結果 |
| --- | --- |
| QPC の周波数の初期化 | static の 64 bit 値を複数 thread が同時に初期化しえた。atomic な読み書きに変えた |
| sample の公開順序 | `sample_count` を先に増やしてから中身を書くので、読む側が書きかけの枠を読めた。`ready` を最後に立て、harness は `ready` の枠だけを読む |
| get_frame の差し替え | consumer を作る前（worker が居ない間）に差し替える。問題なし |
| get_frame の復元 | 成功・失敗・取消・timeout のどの経路でも、consumer を stop・close して worker が終わった後に戻す。問題なし |
| 各境界の `first_*` | 最初の 1 回を数えた thread だけが書く。書き込みの途中を別 thread が読みうるが、判定に使うのは書き出しが終わった後の値だけである（header に明記済み） |

合成だけの時間を検査や encoder と分けて比べるため、`image_ns_total`（合成後の画像の要求から戻りまでの
合計）を足した。

## 2. コスト分析

### MLT が処理する画素

[事実] MLT 7.36.1 の affine（`transition_affine.c` の `sliced_proc`）は、layer ごとに出力の全画素を
走査し、各画素で素材座標を倍精度で計算する。素材の範囲に入った画素すべてで、双線形補間と float の
source-over を行う。素材が全画面の透過 PNG なら、字形の有無によらず 2,073,600 画素すべてが対象になる。
`fill`・`distort` を指定しているので、素材は配置の矩形の大きさで要求される（等倍なら元の大きさのまま。
拡縮があると Qt の `QImage::scaled` が先に縮拡する）。

### 字形の範囲と、frame ごとの合成対象

[事実] v4 の数式 99 clip（成果物 39 種）を `scripts/math-sparse-p1-cost.py` で数えた
（`v4-cost-pixels.json`。10 frame ごとの layer 数と画素数を含む）。

| | 値 |
| --- | --- |
| 字形の範囲 / 全画面 | 最小 0.006%、中央値 0.125%、平均 0.38%、最大 4.9% |
| 有効な数式 layer / frame | 最小 12、平均 27.5、最大 40 |
| 合成対象の画素 / frame（全画面・現在） | 平均 5,693 万、最大 8,294 万 |
| 同（左上原点を保つ切り出し） | 平均 1,672 万（29.4%）、最大 2,412 万 |
| 同（字形の範囲 + 余白 2 画素） | 平均 128 万（2.2%）、最大 458 万 |
| 切り出せる clip | 97 / 99（拡縮する 2 clip は全画面のまま数えた） |

### 並列度

[事実] 16 層・120 frame の fixture で render thread 数だけを変えた（encoder の thread 数は 0 = 自動のまま）。

| render thread | render 秒 | 合成 ms/frame | CPU 時間 / 経過時間 |
| --- | --- | --- | --- |
| 1 | 23.7 | 187.1 | 4.18 |
| 2 | 26.4 | 232.9 | 4.51 |
| 4（製品） | 26.2 | 229.8 | 4.37 |
| 8 | 26.2 | 239.8 | 4.45 |
| 16 | 26.0 | 239.6 | 4.50 |

render thread を増やしても速くならない。1 本が最も速かった。実効の並列度は 4.2〜4.5 core で頭打ちで、
この PC の論理 32 core を使えていない。MLT の affine は 1 つの transition を lock して合成するので、
同じ transition を通る frame は直列になる（`transition_affine.c` は `threads` が 1 以外のとき合成の間も
lock を持つ）。CPU を使っているのは、affine の slice thread と x264 である。

### 主なコストの内訳

- 層の数に比例する部分: layer ごとの全画素の合成（上の表）。切り出しで減らせる。
- 層の数に比例し、切り出しでは減らない部分: layer ごとに出力の全画素を走査して素材座標を計算する処理、
  素材 frame の取得、motion のある clip に付く qtcrop（全画素を QPainter で描き直す）。
  字形の範囲だけを渡しても 48 層で 112 ms/frame が残った（1 層あたり約 2.3 ms）。
- Project の大きさに比例する部分: 下の「v4 全体」を参照。

## 3. 試作

`src/app/timeline_export.cpp` と `src/media/mlt/mvm_mlt_export.c` に、既定では使わない経路を足した。

- 切り出すのは、どの区間も**等倍・回転なし・shear なし・crop なし**で、上位 track にある静止の数式だけ。
  Write・変形・クロスディゾルブの incoming・拡縮する clip は、指定によらず全画面で渡す。
- 字形（alpha > 0）の範囲に、透明な余白を 2 画素残す。双線形補間は隣の画素を読むので、余白が無いと
  縁の画素が変わる。
- 配置の矩形を、切り出した範囲の分だけずらす（`MvmExportClip::source_*`）。MLT 層は条件を満たさない
  clip を拒否する。
- MLT は素材を「高さ × (幅 / 高さ)」を int へ切り捨てた幅で要求する。この式が元の幅に戻らない大きさだと
  1 画素縮められるので、戻る幅になるまで透明な余白を足す。

単純な切り抜き・再配置で同じ結果になるとは仮定しなかった。結果が変わりうる点と、確かめた結果:

| 点 | 評価 |
| --- | --- |
| 範囲の外の画素 | 現在は alpha 0 の素材を合成している。alpha が 254・255 の下地では結果が変わらないことを、全画素比較で確かめた（左上原点を保つ切り出しが完全一致） |
| 縁の補間 | 余白 2 画素で、補間が読む隣の画素は切り出す前と同じ（透明）になる |
| 端数位置 | MLT は素材座標を binary32 で持つ。原点をずらすと座標の大きさが変わり、端数部分の丸めが変わる。補間結果を切り捨てる境界（例: 255 × 0.6 = 153）にある画素で 1 階調ずれる。偶然ではなく、同じ画素で毎 frame 起きる |
| 拡縮 | MLT は素材を矩形の大きさへ Qt で縮拡してから置く。切り出した画像を縮拡した結果は、全体を縮拡してから切り出した結果と一致しない（寸法の int への切り捨てと、縮拡の kernel の位相が変わる）。対象外にした |
| 回転・shear | 矩形の中心を軸に回るので、矩形を変えると軸が動く。補正が要る。対象外にした |
| crop | qtcrop の矩形は素材 frame の大きさに対する値になる。対象外にした |
| opacity・fade | 矩形と独立なので影響しない（全画素比較で確認） |

**MLT の既存 API で達成できる範囲**: 等倍・回転なし・crop なしの静止 layer は、API だけで切り出して
渡せる。完全一致を保てるのは原点を動かさない切り出しだけである。
**独立した合成処理が要る範囲**: 字形の範囲そのものを端数位置でも完全一致で合成すること、拡縮・回転を
含む layer を切り出すこと、layer ごとの全画素の走査そのものを無くすこと。これらは MLT の affine の
座標計算と丸めを自前で再現するか、同時に見える部分式を MLT へ渡す前に 1 枚へまとめる必要がある。
後者は layer ごとの切り捨てを 1 回にまとめるので、pre-YUV は現在と完全一致しない。

## 4. 検証

既存の fixture は変えず、比較用の fixture を足した（`tests/harness/math_score_export_parity.cpp` の
`cmp-*`）。同じ process・同じ build で **baseline → candidate → baseline（2 回目）** の順に書き出し、
candidate の pre-YUV を baseline と全 frame・全画素（4 channel）で比べる。

- 2 回目の baseline が 1 回目と全 frame 同じでなければ、比較は不成立（`COMPARE_INVALID`）にする。
- 比べられなかった frame があれば不成立にする。一致には数えない。
- 完全一致（終了コード 0）、1 階調以内（13）、それを超える（14）、不成立（15）を分ける。
- 対照: baseline の 1 画素を 2 階調ずらすと 14 で落ちる（両方の候補で確認）。既存の negative control
  4 種も期待どおりだった。

| --- | --- | --- |
| `cmp-integer` | 数式 1 層、整数位置 | 120 |
| `cmp-fraction-fade` | 数式 1 層、端数位置、末尾 30 frame が fade | 120 |
| `cmp-layers-16` | 16 層（強調の layer が同じ位置に重なる）、fade あり | 120 |

### v4 全体（製品の timeout のまま）

[事実] 主の書き出しそのものを試作の渡し方にして、v4 全体を製品の `timeout_ms`（600000）のまま書き出した。
どちらも完了しなかった。診断の上限 720 秒で取り消した（`CAPPED_WHILE_PROGRESSING`。停止ではない）。

| 渡し方 | 720 秒で合成できた frame | 1 frame の時間 | CPU 時間 / 経過時間 |
| --- | --- | --- | --- |
| 全画面（修正後、2026-10-11 の記録） | 240 秒で 919 | 0.26 秒 | 約 4.3 |
| 左上原点を保つ切り出し | 2476 / 6840 | 0.25〜0.35 秒 | 1.8〜2.2 |
| 字形の範囲そのもの | 2977 / 6840 | 0.19〜0.34 秒 | 1.5〜1.8 |

- 同じ区間（20〜22 秒）を区間の fixture で書き出すと 0.067 秒/frame（字形の範囲）なのに、Project 全体の
  中では 0.24 秒/frame かかる。画素と layer は同じなので、差は Project 全体の graph の大きさから来る。
- CPU は 1.5〜2.2 core しか使えていない。直列の処理が支配している。
- [事実] 上限で採った stack のうち関数名を解決できた 1 回は、実行中の thread が
  `affine transition → mlt_property_get_string_tf → mlt_animation_serialize_cut_tf` にいた。
  残り 3 回は、合成の再帰が深く、採った 40 frame に load 先を決める frame が入らなかった（解決できていない）。
- [推測] 間引いた後も、v4 は 99 clip で 19632 個の keyframe を持つ。区間の fixture は clip を 120〜180
  frame に切るので 1 clip の keyframe が少ないが、Project 全体では長い clip が複数の変化区間の
  keyframe をすべて持つ。affine が毎 frame それを文字列へ直す処理が残っている。stack 1 回と上の比較からの
  説明で、keyframe 数を変えて測ってはいない。
- [事実] この 2 回の run は、render の開始から 720 秒以上たっても `timeout_ms` = 600000 の失敗にならなかった。
  MLT 層の待ち loop は `Sleep(20)` の回数で経過時間を数えており（`mvm_mlt_export.c`）、実時間より遅く進む。
  契約は変えていない。[AGENTS.md](../AGENTS.md) の「`Sleep` 回数で経過時間」と同じ形である。

## 5. 判断と、さらに必要な変更

**意味的に同一な合成を実現できるか**

- 完全一致: 左上の原点を保つ切り出しで実現できる（比較した 840 frame すべて）。効果は 2 倍前後に留まる。
- 1 階調以内: 字形の範囲そのもので実現できる。差は字形の縁の半透明の画素に限られ、1 階調を超えない。
  ただし現在の pre-YUV とは一致しないので、採るなら parity の基準（現在は MLT の合成そのもの）を
  どう置くかを先に決める必要がある。
- 拡縮・回転・crop を含む layer は、どちらの方法でも切り出していない。

**製品の 10 分 timeout の見込み**

この試作だけでは達成できない。区間の fixture の速さ（字形の範囲で 0.067〜0.12 秒/frame）が Project 全体で
出たとしても 6840 frame で 460〜820 秒かかり、余裕が無い。実際の Project 全体では 0.19〜0.34 秒/frame で、
全体に 20〜40 分かかる計算になる。

**さらに必要な変更**（未着手。効果は測っていない）

1. keyframe の文字列化を Project の長さから切り離す。たとえば 1 clip の transition を、値の変わる区間と
   変わらない区間ごとに分け、1 つの transition が持つ keyframe を区間の長さまでに抑える。
   画素は変わらない見込みだが、MLT の graph の形が変わるので全画素比較が要る。
2. layer ごとの全画素の走査と lock による直列化を減らす。同時に見える部分式を書き出し前に 1 枚へまとめるか、
   数式 layer の合成を MLT の外で行う。どちらも pre-YUV が現在と完全一致しなくなる。
3. 1 と 2 の後で、字形の範囲だけを渡す方法（この試作）の効果を Project 全体で測り直す。
4. `timeout_ms` の数え方（`Sleep` の回数）と、進行中でも失敗にする契約をどうするかは別に決める。
