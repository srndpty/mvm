# ADR 0001: MLT 7 を mvm のリアルタイム preview engine として採用しない

- 状態: 承認
- 日付: 2026-08-06
- 対象: mvm Phase 0（技術スパイク）
- 根拠文書: [../phase0-decision.md](../phase0-decision.md)

## 決定

**MLT 7.36.1 / MSYS2 UCRT64 の現行 CPU・RGBA 経路を、
mvm の統合編集・リアルタイム preview engine として採用しない。**

## 文脈

mvm は YouTube 向けの技術・数学解説動画を主対象とする、
Windows 用ノンリニア動画編集ソフトである。
編集・プレビュー・書き出しエンジンを内製するか既存フレームワークに載せるかが、
製品全体のコスト構造を決める最大の分岐点だった。

第一候補は MLT 7 だった。Shotcut / Kdenlive の実績があり、
LGPL であり、必要なモジュール (avformat / qt / plus / core) が揃っている。
懸念は Windows における公式ビルドが MSYS2 / mingw-w64 前提であり、
MSVC ビルドが上流非サポートである点だった。

Phase 0 の唯一の成果物は **MLT 採用可否の判断根拠**である。
S0〜S7.1 を実施し、S8〜S15 を実施せずに早期 S16 として判定した。

想定する最大編集規模は 1080p60、動画 2 層 + 音声 2 層 + 文字 1 層、尺 20 分程度。
4K は素材としてのみ扱い、proxy 前提とする。

## 決定理由

判定規則は計画 §10 の **MUST 全充足**である。

**1. 連続 preview の fps が基準の 40% しか出ない (M7 不合格)**

1080p60 / 5 トラックで最良 **19.85 fps** (`real_time=-1`)。基準は 50 fps。
これは Qt を一切含まない、MLT が RGBA を作り終えるまでの値である。
レンダースレッドを増やすと悪化した。

**2. proxy 化しても上限が変わらない (M8 不合格)**

preview で使う video source を**全て** 540p proxy にして **19.67 fps**。
4K original の 10.00、V1 だけ proxy の 14.88 からは改善するが、
**1080p native の 19.85 とほぼ同じ**である。
素材の解像度を下げても 20 fps 付近が上限であり、
律速は解像度ではなく合成と RGBA 生成そのものである。

したがって「常時 proxy を使う条件付き採用」は成立しない。

**3. 単独の低コスト回避策が見つからなかった (参考値)**

ablation で必須機能 (文字レイヤ、PiP) を丸ごと外しても最良 **35.84 fps**。
製品で使える構成では 21.53〜31.10 fps。いずれも基準 50 に届かない。

**[注意] ablation の値は再現性を確認できていない。**
2026-08-06 の再測定で、同じ scenario が run ごとに 2.5 倍ばらつく現象が出た
(ホスト側の要因。原因未特定)。**この項目は決定の主たる根拠ではない。**
決定を支えているのは 1 と 2 であり、
M8 は独立に 9 回測って 18.74〜19.83 fps に収まっている。

**4. seek 速度も 1000 点の最終確認で不合格 (M5)**

p95 82.7ms は基準内だが、観測 max **2998.0ms** が基準 400ms を超過した。
超過は各 run の 1 回目 (cold) のみで、warm 3039 サンプルは max 132.0ms。
**この項目単独では判定を左右しない**が、記録として残す。

**5. Qt 経路 (S12) を測っても結果は変わらない**

S12 で加わるのは `QSGTexture` へのアップロード、UI スレッドのフレーム時間、
音声クロック追従、垂直同期である。
**Qt 経路は MLT が作った RGBA を受け取る側であり、供給側より速くならない。**
供給側が既に基準の 40% であるため、S12 の実施は判定を変えない。

## この決定が言っていないこと

範囲を広く読み替えないために明示する。

- **MLT が一般に使えないとは言っていない。**
  測ったのは *この構成* (7.36.1 / UCRT64 / CPU / RGBA / 5 トラック 1080p60) だけである。
  Shotcut / Kdenlive が実運用されている事実と矛盾しない。
- **書き出し (export) に使えないとは言っていない。** 書き出しは測っていない。
- **オフラインレンダに採用するとも言っていない。** これも測っていない。
  M9〜M11 (エフェクト / 書き出し / preview-final 一致) を一つも実施していないため、
  **未評価**である。肯定も否定もできない。
- **別の MLT 経路 (GPU / movit / SDL consumer) が不可とは言っていない。** 測っていない。

## 未評価のまま残る項目

M9 (エフェクト)、M10 (書き出し)、M11 (preview/final 一致)、
M13 (clean VM 起動)、M14 (UI 応答性)、M15 (抽象化)、M16 (安定性)、
M1 の残り (from-source ビルドの 2 回連続再現)、
all-video proxy での M6 (scrub) 正式 8 条件。

## 結果

**採用しない経路**

- MLT を mvm のリアルタイム preview engine として使う
- MLT を統合編集エンジン (Project Model → MLT tractor → consumer) として使う

**次に検討する代替案** (計画 §9 を今回の所見で更新)

落ちた理由は **アーキテクチャ的な性能上限**であって、
Windows のビルド・配布・ABI ではなかった。この事実が順位を決める。

1. **libavcodec / libavfilter ベースの自作エンジン + GPU 合成**
   落ちた原因そのものを置き換える。mvm は必要な機能集合が小さい
2. 自作の軽量 preview エンジン + final render は FFmpeg `filter_complex`
3. GStreamer + GES — **順位を下げる。** 利点の MSVC 公式ビルドは
   今回問題にならなかった論点であり、合成性能が改善する根拠が無い
4. MLT を fork して vendoring + パッチ — **順位を下げる。**
   欠陥が局所的でなく合成経路全体の上限であるため

**保持する成果**

以下はいずれも backend 非依存に作ってあり、代替案でもそのまま使える。

- 検証素材の決定論的生成とフレーム固有マーカー
- `mvm_bench` の計測手法 (delivered/effective fps の分離、seek の marker 照合)
- proxy path resolver の required / optional 契約と fail-closed
- scenario 形式と `IMediaEngine` を見据えた層分け

**副次的に確定した事実 (MLT に依存しない)**

- MSYS2 UCRT64 統一でビルド・実行とも問題は出なかった
- 日本語を含むパスは読み込み・書き出しとも動作した
- ABI / 配布は今回の不採用理由ではない

## 補足: 判定を左右しなかった懸念

Phase 0 開始時に最大のリスクと見ていた
「Windows での MSVC 非サポート」「ABI 混在」「日本語パス」は、
**いずれも実際には障害にならなかった。**
落ちたのは性能である。リスク想定と実測結果が食い違った事例として記録する。
