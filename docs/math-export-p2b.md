# 数式 layer の書き出し高速化 P2-B: transition の固定費と分け方

2026-10-12。[P2-A](math-export-p2a.md) で、Project 全体（v4）が遅い主因は MLT が毎 frame 行う animation の
文字列化だと確かめた。transition を区間ごとに分ける試作は画素を保ったまま文字列化を消したが、
transition が 120 から 766 に増え、合成時間の改善は一定しなかった。ここでは transition 1 つの固定費を測り、
分け方を変えて利益が安定するかを調べた。

**製品の経路は変えていない。** 試作は既定で無効のままである（`MvmExportObserver` の `diagnostic_*`。
製品は observer を渡さない）。`timeout_ms` の契約と既定値、keyframe の間引き、P1・P2-A の成果物と
FAIL/PASS/INVALID の記録は変更していない。commit・push はしていない。

証拠は `build/math-export-p2b-20261012/`。run ごとの `identity.json` に、その計測に使った source と runtime の
SHA-256、git の HEAD と作業 tree の状態、実行した variant と回数がある。benchmark と全画素比較は同じ
build（整形後の source）で行い、その後 source は変えていない。

## 判定

| 採用の条件 | 結果 |
| --- | --- |
| 1. 同じ負荷で利益が再現する | **満たさない**。前半は遅くなり、中盤は速くなり、後半はほぼ同じ |
| 2. transition の固定費が分かっている | 満たす。植えた transition 1 つにつき毎 frame 0.29〜0.35 ms |
| 3. 画素の完全一致 | 満たす（下の「画素」。4 方針とも） |
| 4. 対照が意図した故障を検出する | 満たす。ただし位置ずれの対照が書き出しの取消で終わる理由は未解明 |
| 5. 外挿と実測の区別 | v4 全体の書き出しは行っていない。全体の所要時間は主張しない |
| 6. 回帰の gate と lint | 下の「gate」 |

**判定: HOLD。** 分割は採らない。事前に決めた 4 つの分け方はどれも、Project 全体で利益が一定しない。

## 1. 位置ずれの対照が不成立になった件（Task A）

P2-A では「keyframe の位置を 1 frame ずらす」故障が、期待した「画素の不一致」（終了コード 14）ではなく
「比較不成立」（15）になった。その結果は P2-A の記録のまま残している。

[事実] 今回、candidate の書き出しが返した理由を report に残すようにして同じ故障を再実行した。
candidate の書き出しは 44 frame を出した所で「書き出しをキャンセルしました」で終わっていた。
出た 44 frame はすべて baseline と 1 階調を超えて違い（最大差 255）、残り 76 frame は作られなかった。

- これは画素の比較による検出ではない。書き出しが完了しなかったために不成立になっている。
  対照の成立には数えない（`invalid-animation-shifted-keys` として別に分類し、期待を 15 にした）。
- [未検証] なぜ取消になるのかは分かっていない。harness は取消を要求しておらず、ずらした keyframe 自体は
  MLT の animation として読める形である（先頭の keyframe が位置 1 になるだけ）。
  「壊れた animation だから失敗した」とは確かめていない。
- 代わりに、animation としては正しく、frame の対応だけが誤っている故障を足した: 各 frame に 1 つ後の
  frame の値を置く（`diagnostic_split_fault` = 4）。書き出しは完了し、95 frame が 1 階調を超えて違う
  （最大差 255）として検出された（終了コード 14）。

## 2. transition の固定費（Task B）

v4 全体の graph のまま、同じ 60 frame を全画面の渡し方で書き出す。64/8 の分け方に加えて、
「変わらない区間」を 240 frame・60 frame ごとにさらに刻む variant を用意した。刻んでも、出力、
1 つの transition が持つ keyframe（両端の 2 個）、同時に有効な transition の数（= layer の数）は変わらない。
変わるのは植えた transition の総数だけである。

| variant | transition | 合成 ms/frame（前半） | （中盤） | （後半） |
| --- | --- | --- | --- | --- |
| 64/8 | 766 | 499.5 | 663.6 | 571.6 |
| 64/8 + 240 frame ごと | 1,293 | 655.7 | 815.6 | 747.0 |
| 64/8 + 60 frame ごと | 3,404 | 1,336.4 | 1,422.6 | 1,496.3 |

[事実]（各 3 回の中央値。pre-YUV は 3 variant とも「分けない」run と一致）

- 合成時間は transition の総数に比例して増える。増分は transition 1 つにつき 0.30・0.32 ms（前半）、
  0.29・0.29 ms（中盤）、0.33・0.35 ms（後半）。
- 同時に有効な transition の数は変えていないので、これは**有効な数ではなく graph の大きさに比例する**
  コストである。affine が矩形を読む回数（`mlt_properties_anim_get_rect`。合成 1 回あたり前半 43、中盤 71、
  後半 49）は、分けない場合を含む全 variant・全 run で同じだった。
- 文字列化の時間は 4.5〜12.2 ms で、ほとんど変わらない。増えた時間は文字列化ではない。
- transition を増やすと実効の並列度が下がる（CPU 時間 / 経過時間が 2.4〜2.8 から 1.6〜1.9 へ）。

測れたもの・測れなかったもの:

| 項目 | 状態 |
| --- | --- |
| 植えた transition の総数 | 測った（`overlay_transitions`） |
| その frame で有効な transition | affine の呼び出し回数から読める（variant の間で同じ） |
| 文字列化の回数と時間 | 測った |
| 合成の時間、実効の並列度 | 測った |
| MLT の service をたどる時間 | **分けて測れていない**。最終 producer の `get_frame` の時間を足したが、値は合成時間とほぼ同じになった（例: 前半・分けない場合で 432 ms と 441 ms）。frame の取得が、合成中の worker が持つ lock を待っていることを示すが、たどる時間そのものと待ち時間を分けられない |
| affine の callback の時間 | 測っていない。MLT の内部で、公開 API からは計時できない |
| mutex の待ち時間 | 直接は測っていない。上の `get_frame` の時間が間接の証拠 |

## 3. 分け方の比較（Task C・D）

事前に固定した variant: 分けない、64/8、128/16、256/32、512/64（変わる区間の上限 / 変わらない区間の下限）。
v4 全体の graph、全画面、前半（1200〜）・中盤（3400〜）・後半（6500〜）の各 60 frame。
variant ごとに 3 回、回と区間ごとに variant の順番を 1 つずつ回した。上限は 60 秒。
7 variant × 3 区間 × 3 回 = 63 run はすべて計測に使えた（完走、または上限で進行中に打ち切り）。
打ち切った run も外れ値も `outcomes.json` と各 directory に残している。

合成 ms/frame。中央値［最小..最大］:

| variant | transition | 前半 | 中盤 | 後半 |
| --- | --- | --- | --- | --- |
| 分けない | 120 | 441.0［430.7..442.7］ | 849.0［761.0..923.5］ | 589.8［544.0..623.6］ |
| 64/8 | 766 | 499.5［488.6..514.0］ | 663.6［641.8..675.8］ | 571.6［549.6..576.8］ |
| 128/16 | 764 | 500.9［483.1..519.0］ | 674.2［661.4..687.5］ | 569.9［569.0..574.4］ |
| 256/32 | 763 | 508.8［505.4..510.3］ | 659.1［651.6..680.7］ | 564.4［558.8..587.0］ |
| 512/64 | 734 | 490.7［485.8..512.2］ | 652.2［623.5..654.4］ | 574.1［564.7..580.7］ |

render の経過時間（秒/合成 1 回、中央値）: 分けない 0.445・0.760・0.590、64/8 0.514・0.677・0.585、
512/64 0.502・0.666・0.585。文字列化（ms/frame、中央値）: 分けない 119.6・287.2・262.0、
分けた場合 4.5・7.4〜7.5・9.2〜9.3（512/64 の後半だけ 26.6）。

[事実]

- 閾値を変えても transition の数は 734〜766 でほとんど変わらず、結果も変わらない。v4 は値の変わる区間と
  変わらない区間が細かく交互に並ぶので、区間の数は閾値ではなく内容で決まっている。
- 分けない場合に対して、前半は 11〜15% 遅く、中盤は 21〜23% 速く、後半は 3〜4% 速い（幅の中）。
- 説明: 分けると文字列化が 115〜280 ms 減り、transition が約 640 増えた分で 190〜220 ms 増える
  （2 の固定費 × 増えた数）。前半は文字列化が小さいので差し引きで損になり、中盤は大きいので得になる。
  64/8 の実測の差（+58、−185、−18 ms）は、この見積もり（+85、−93、−33 ms）と向きが合う。
  中盤は見積もりより大きく改善している（分けない場合の中盤は幅が 761〜924 ms と大きい）。

適応的な分け方（任意）は試作していない。2 の固定費から見て、transition を増やさずに文字列化を減らせる
余地は小さい: transition を 1 つ増やすと Project の全 frame で 0.3 ms かかり、6840 frame で約 2 秒になる。
1 clip の keyframe を半分にして得られる文字列化の減少がこれを上回るのは、keyframe が数百あり、かつ
長く表示される clip に限られる。見積もりであり、測ってはいない。

baseline は製品の全画面・分割なし。同じ process で baseline → candidate → baseline の順に書き出し、
candidate を全 frame・全画素（4 channel）で比べる。許容差は使わない（完全一致だけを成立とする）。

[事実] 分け方 4 つ（64/8、128/16、256/32、512/64）それぞれで、9 fixture・960 frame が全画素・完全一致した
（合計 3840 frame）。未比較 0、2 回目の baseline との不一致 0。比べた範囲:

- 比較 fixture 6 本（整数位置、端数位置と fade、16 層、48 層、v4 の 20〜22 秒、88〜91 秒）と、
  v4 の前半・中盤・後半の区間 3 本。分け方 4 つそれぞれで、全 frame。
  端数位置、不透明度の補間、変わる区間と変わらない区間、区間の境界（transition の in/out が変わる frame）、
  隣り合う数式 layer、拡縮する layer を含む区間、clip の先頭と末尾を含む。
- v4 全体の graph の前半・中盤・後半: benchmark の全 run の digest を、同じ区間の「分けない」run と比べた。
  分け方 4 つは各 180 frame（60 frame × 3 回）で不一致 0。刻んだ variant も不一致 0

## 5. timeout の数え方（別件）

P2-A の修正案を確認した。変更は入れていない。

- 対象は MLT 層の待ち loop 2 か所（sequential と tractor）。どちらも `Sleep(20)` の回数に 20 を掛けて
  経過時間としている。`mlt_export_timeout_accounting_deviation` が現状（`timeout_ms` = 1000 が実時間
  約 3.4 秒で timeout）を記録している。
- 修正: loop に入る前に単調増加の時刻を取り、毎回「いま − 開始 ≥ timeout_ms」で判定する。
- 保つもの: 開始からの絶対時間で、進行中でも失敗にする意味。取消の確認を loop の毎回、timeout の判定より
  先に行う順序（取消と timeout が同時に成り立つときは取消として返す）。既定値 600000 ms。
- 分割の計測とは独立である。この修正を入れると、いま実時間 10 分を超えても通っている書き出しが失敗に
  変わるので、入れる時期は別に決める。

## 6. 次の段階

分割は HOLD のままにする。transition を増やす方法では、文字列化を消した分を transition の固定費が
打ち消す。残っているコストは、どれも MLT の affine と tractor の実行の仕方から来ている:

- animation の付いた property を読むたびの文字列化（P2-A）。
- 植えた transition の数に比例する毎 frame の固定費（今回）。
- transition の lock による直列化（render worker を増やしても速くならない。P1）。
- layer ごとの全画素の合成（P1）。

次に調べる候補:

1. **MLT の affine の実行経路**。毎 frame の固定費 0.3 ms が何に使われているか（frame の取得、property の
   読み出し、lock）を、MLT を診断用に作り直して計る。公開 API の外からは、これ以上分けて測れない。
2. **数式 layer の合成を MLT の外で行う設計の検討**。上の 4 つをまとめて避けられるが、pre-YUV は現在と
   完全一致しなくなる（P1）。設計と parity の基準の検討までとし、この段階で実装へは広げない。
